# Spring Capability Coverage Map

Spice aims to cover as much of the practical Spring Boot and Spring Modulith platform as provides value to Go developers. This is a living product map, not a promise to port Java classes verbatim.

| Core | Dependency injection | Exact-type catalog/graph, deterministic direct-call constructor/rollback, and guarded generated-file application | available |
| Core | Auto-configuration | `@Application` provides safe generated command conventions; explicit typed `@management.Enable`, `@observability.Logging`, and selected-starter `@otel.Enable` companions are compile-time validated, carried in immutable IR, and deterministically composed without dependency-presence activation; broader conditions follow | in-progress |
| Core | Starters and dependency alignment | A public strict `spice.starter/v1` SDK and committed `spice.starters/v1` repository selection provide fail-closed compatibility and explicit constructor/annotation activation without dependency-presence semantics; the CLI loads constructor packages as isolated roots in the shared typed program, validates exact provider signatures/graphs, and emits direct calls with cleanup/rollback and provenance hashing; only active starters undergo bounded, read-only, offline Go module graph validation for exact reviewed versions and replacement identity; OpenTelemetry proves generated annotation-role composition while PostgreSQL, Redis, OIDC, and OAuth2-client retain explicit constructor manifests | in-progress |

## Coverage rules

Every new area must define:

1. The developer-facing API.
2. The generated or runtime behavior.
3. Failure diagnostics.
4. Security defaults.
5. Unit and integration tests.
6. A runnable example.
7. The intended Spring capability relationship.
