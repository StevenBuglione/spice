# Dogfooding readiness

Spice may be used to compose Spice-owned applications and libraries only while
its compiler bootstrap remains an ordinary Go dependency. Self-hosting must
improve the repository's application structure without making the compiler
dependent on generated output that only that compiler can produce.

## Bootstrap boundary

The dependency direction is:

```text
ordinary Go toolchain
    -> cmd/spice + compiler + generator + guarded filesystem writer
    -> generated Spice application packages
    -> Spice-owned applications and opt-in library composition
```

The reverse edge is forbidden. `cmd/spice`, `internal/cli`, and all compiler
packages must not import any `internal/spicegen/...` application package.
Generated code may import public Spice runtime packages, but the compiler
bootstrap must build offline from the repository vendor graph with no generated
application present.

This means "dogfood Spice" does not mean rewriting the parser, type checker, or
renderer as runtime beans. It means using Spice where its application model
adds value: command composition, configuration, lifecycle, module boundaries,
observability, HTTP surfaces, and reviewed integrations.

## Automated proof

`make bootstrap` performs a destructive recovery exercise only inside a newly
created temporary directory:

1. build `cmd/spice` with `-mod=vendor`, `-trimpath`, and network access off;
2. audit its complete dependency list for a generated-application dependency;
3. create a valid handwritten Go application with no `.spice` manifest or
   `internal/spicegen` directory;
4. generate, build, and execute that application offline;
5. snapshot every owned manifest and generated byte;
6. remove the owned output and regenerate it from zero;
7. require byte-for-byte equality;
8. corrupt an owned generated Go file and require the freshness check to fail
   with an actionable manual-edit diagnostic;
9. remove only the temporary owned output, regenerate again, compare it with
   the original snapshot, and execute the recovered application.

The same proof is a mandatory final stage of `make verify`. It complements the
renderer determinism tests, committed application freshness checks, offline
vendor tests, generated-code compilation, executable Commerce/Petclinic
smoke paths, and GoLand package Run/Debug suite.

## Library composition contract

Spice libraries may contribute defaults through ordinary Go imports. A caller
explicitly blank-imports a package whose final path segment is
`autoconfigure`; that package contains one statically decoded
`SpiceAutoConfiguration` descriptor. Go's `go.mod`, `go.sum`, vendor data, and
`replace` directives own versioning and provenance. Spice does not scan the
module graph for ambient candidates and does not execute package `init`.

Application beans replace fallback defaults before construction. Required
dependencies that are unavailable make a default inactive. `spice beans
--explain` reports selected, replaced, and inactive defaults with module,
version, replacement, and dependency-review provenance.

Tests compose generated applications through target-specific, exact-type
`BeanOverrides`. `bean.Replace` supplies a value and `bean.ReplaceFactory`
supplies construction plus cleanup. Replacements occupy the original provider
position and therefore use the same downstream dependency, reverse rollback,
module cleanup, and shutdown behavior. There is no mutable test container,
reflection, or bean-name lookup.

## First dogfood change

The first production dogfood change should be deliberately small and
reversible:

1. select one Spice-owned command or service boundary with useful
   configuration and lifecycle behavior;
2. keep the existing ordinary-Go entrypoint available for one transition
   commit;
3. generate into a dedicated `internal/spicegen/<target>` package;
4. prove a clean bootstrap, normal and failure execution, debugger navigation,
   and exact rollback;
5. remove the old assembly only after byte-stable regeneration and the complete
   repository gate pass.

Compiler analysis and generation packages are not candidates for that first
slice. Any proposed self-hosting change that weakens the bootstrap boundary,
requires generated code to rebuild the compiler, or introduces runtime
reflection/global registration must be rejected.
