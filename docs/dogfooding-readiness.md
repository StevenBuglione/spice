# Spice self-hosting and recovery

Spice's production command is a Spice application. Its command dependency is
selected by imported auto-configuration, constructed through committed
generated Go, exposed through typed `Components`, and owned by the generated
lifecycle. A separate ordinary-Go stage-zero command keeps that self-hosting
recoverable.

## Bootstrap boundary

The dependency direction is:

```text
ordinary Go toolchain
    -> cmd/spice-bootstrap
       -> internal/cli + compiler + generator + guarded filesystem writer
       --generates/checks--> internal/spicegen/spice

cmd/spice
    -> internal/spicegen/spice
       -> internal/autoconfigure.DefaultCommand
       -> internal/cli.Command
```

The reverse edge into stage zero is forbidden. `cmd/spice-bootstrap`,
`internal/cli`, and all compiler packages must not import an
`internal/spicegen/...` package. Only the production entrypoint imports the
dedicated `internal/spicegen/spice` target. That target may call ordinary
runtime and CLI packages, but those packages never import it.

The application marker is `internal/spiceapp.Spice`. It requires the typed
`*internal/cli.Command` root and declares its module dependency on
`internal/cli`. The blank-imported `internal/autoconfigure` package contributes
the reviewed fallback `DefaultCommand` factory. The generated graph therefore
uses the same import-driven default selection, direct construction, typed test
override, configuration, and lifecycle behavior offered to applications.

Self-hosting does not make the parser, type checker, renderer, or guarded
filesystem writer runtime beans. Those packages remain ordinary Go so the
recovery compiler has no bootstrapping cycle.

## Automated proof

`make bootstrap` performs a destructive recovery exercise only inside a newly
created temporary directory:

1. build `cmd/spice-bootstrap` with `-mod=vendor`, `-trimpath`, and network
   access off;
2. audit its complete dependency list and reject every generated-application
   dependency;
3. use stage zero to require the committed production `Spice` target to be
   fresh;
4. build `cmd/spice` offline and require its dependency graph to contain the
   exact `internal/spicegen/spice` target and no other generated target;
5. execute the production `version` command, then use the production command
   itself to recheck its generated target;
6. create a valid handwritten Go application with no `.spice` manifest or
   `internal/spicegen` directory;
7. generate, build, and execute that application offline;
8. snapshot every owned manifest and generated byte;
9. remove the owned output and regenerate it from zero;
10. require byte-for-byte equality;
11. corrupt an owned generated Go file and require the freshness check to fail
   with an actionable manual-edit diagnostic;
12. remove only the temporary owned output, regenerate again, compare it with
   the original snapshot, and execute the recovered application.

The same proof is a mandatory final stage of `make verify`. It complements the
renderer determinism tests, committed application freshness checks, offline
vendor tests, generated-code compilation, executable Commerce/Petclinic
smoke paths, and GoLand package Run/Debug suite.

## Library composition contract

Spice libraries may contribute defaults through ordinary Go imports. A caller
explicitly blank-imports a package whose final path segment is
`autoconfigure`; that package contains one statically decoded
`SpiceAutoConfiguration` descriptor. Go's `go.mod`, `go.sum`, vendor data, and
`replace` directives own versioning and provenance. Spice does not scan the
module graph for ambient candidates and does not execute package `init`.

Application beans replace fallback defaults before construction. Required
dependencies that are unavailable make a default inactive. `spice beans
--explain` reports selected, replaced, and inactive defaults with module,
version, replacement, and dependency-review provenance.

Tests compose generated applications through target-specific, exact-type
`BeanOverrides`. `bean.Replace` supplies a value and `bean.ReplaceFactory`
supplies construction plus cleanup. Replacements occupy the original provider
position and therefore use the same downstream dependency, reverse rollback,
module cleanup, and shutdown behavior. There is no mutable test container,
reflection, or bean-name lookup.

The Spice target's handwritten tests construct the real generated
`Application`, assert typed command availability and lifecycle transitions,
and replace the command with `bean.ReplaceFactory` to prove exact construction
and idempotent cleanup. `make smoke` additionally runs production generation
freshness and `spice beans --explain`, requiring the imported fallback and its
dependency-review provenance to remain observable.

## Generated source boundary

Production target orchestration is split into contracts, configuration,
providers, assembly, lifecycle, and command units. Every contributing
handwritten file maps to one adapter below
`internal/spicegen/spice/sources/.../<source>_spice_gen.go`. Source directories
named `internal` or `vendor` are represented as `internal_` or `vendor_` in the
generated import path so Go's special package rules cannot make an adapter
unimportable. Exact original paths and source ranges remain in file headers and
the schema-5 ownership manifest.

Any future self-hosting change that gives stage zero a generated dependency,
introduces a runtime container, or makes recovery require the production
generated target must be rejected.
