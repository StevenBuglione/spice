# Deterministic Generated Go, Ownership, and Freshness

Date: 2026-07-24

## Question

After Spice has one typed Go program, resolved annotations, a validated provider catalog, and a deterministic provider dependency graph, what generated-code contract should it use so application bootstrap remains ordinary Go while generation is reproducible, reviewable, safe to apply, easy to verify in CI, and compatible with Go modules, workspaces, build constraints, and offline builds?

## Decision summary

Spice should treat code generation as a pure compiler phase followed by a narrow filesystem-application phase:

```text
immutable typed program and validated Spice IR
  -> deterministic generation target
  -> in-memory generation plan
  -> canonical generated Go bytes and manifest
  -> check-only comparison or guarded filesystem apply
  -> ordinary go build / go test
```

The recommended contract is:

1. The compiler core returns a deterministic `Plan`; it does not write files.
2. A generation target names exactly one main module, generated package import path, output directory, package patterns, and normalized Go build context.
3. The first implementation emits one target-scoped generated package and one generated Go file, plus one manifest.
4. Generated bytes contain no timestamps, absolute paths, random values, hostnames, current working directory, map iteration order, or secret environment values.
5. Imports, declarations, diagnostics, and manifest entries are sorted by stable semantic identity.
6. Every generated Go file starts with the standard `// Code generated by Spice. DO NOT EDIT.` marker.
7. A committed manifest records schema version, target identity, safe build-context metadata, stable input fingerprint, relative file paths, and SHA-256 content hashes.
8. `spice generate --check` renders entirely in memory and exits non-zero when committed output is missing, stale, unexpectedly present, or locally modified.
9. `spice generate` acquires an exclusive target lock, writes temporary files beside their destinations, validates them, replaces files, and writes the manifest last as the commit marker.
10. Spice never deletes or overwrites an unowned path. Stale generated files are removable only when the prior manifest owns them and their current hash still matches that manifest.
11. Unchanged output is not rewritten, preserving mtimes and Go build-cache effectiveness.
12. Generated files are checked into source control for the initial product model so review, `go build`, `go test`, and downstream module use do not require Spice to run implicitly.
13. `go generate` may be offered as a convenience wrapper, but generation is never assumed to run during `go build` or `go test`.
14. Multi-module output, multiple applications per module, test-specific graphs, context-matrix generation, and incremental persistent caches are later bounded slices.

This contract should be settled before generated provider invocation or lifecycle code is implemented. Otherwise the first bootstrap generator will accidentally define file ownership, stale-code behavior, import naming, path safety, and reproducibility through incidental implementation choices.

## Findings and decisions

### 1. Generation must be pure before it touches the filesystem

The compiler-facing API should consume only already validated inputs:

- the exact issue #8 typed program;
- issue #11 resolved annotation occurrences;
- issue #13 provider metadata;
- issue #17's validated graph and stable dependency-first order;
- later lifecycle, route, module, configuration, and starter IR;
- one explicit generation target.

It must not:

- call `packages.Load` again;
- reparse files;
- walk the repository;
- infer providers or modules a second time;
- execute provider functions;
- read process-global registries;
- write files;
- access the network;
- mutate `go.mod`, `go.sum`, or `go.work`.

A conceptual boundary is:

```go
type Target struct {
    ID                string
    ModulePath        string
    ModuleRoot        string // live, non-serializable execution detail
    PackagePath       string
    OutputDir         string // module-relative slash path
    PackagePatterns   []string
    Build             BuildContext
}

type Plan struct {
    Target   TargetSummary
    Files    []File
    Manifest Manifest
}

type File struct {
    Path    string // module-relative slash path
    Mode    fs.FileMode
    Content []byte
    SHA256  string
}

func Render(program *load.Program, model ApplicationModel, target Target) (Plan, []Diagnostic)
```

Exact exported names may change. The important boundary is that `Render` is deterministic and testable without a writable repository.

### 2. The target is an explicit product concept

A generator cannot safely infer a single output location from arbitrary `./...` roots, especially in a workspace containing several modules or applications.

The first target model should require:

- one main module path and root;
- one application ID;
- one generated package import path;
- one module-relative output directory;
- ordered package patterns passed to the existing loader;
- normalized build flags and target platform inputs;
- one generated-code schema version.

The application ID must be a stable logical name, not a directory basename guessed from the current working directory.

The first implementation should reject:

- output spanning more than one module;
- generated files outside the selected main module;
- two targets owning the same output path;
- an output package that would import itself;
- a source package importing the generated package and thereby creating a cycle;
- absolute or parent-traversing output paths;
- ambiguous workspaces where no target module was selected.

Multi-module workspaces should remain loadable for analysis, but one generation operation should own files in one selected module only.

### 3. Use a target-scoped generated package rather than mixing generated declarations into user packages

The default first-slice layout should be conceptually:

```text
<module root>/
  internal/
    spicegen/
      zz_spice_gen.go
  .spice/
    generated.json
```

The exact configurable output path can be decided in the implementation issue, but the default should be a dedicated internal package.

Benefits:

- ownership is visually obvious;
- generated names cannot collide with user declarations in many packages;
- the package can import application providers without changing those packages;
- the generated graph is inspectable in one place;
- deletion and freshness checks have a small, explicit surface;
- ordinary Go `internal` visibility prevents unrelated external modules from treating bootstrap internals as a public API.

Application packages must not import the generated package. A handwritten or separately scaffolded `main` package may import it and call the generated constructor.

The initial slice should generate one Go file. Splitting output by feature or size should be deferred until measured file size or reviewability demonstrates a real need. A single file sharply reduces stale-file and partial-apply complexity.

### 4. Stable semantic order controls every emitted sequence

Generation must never depend on:

- Go map iteration;
- filesystem traversal order;
- source discovery order when the semantic model defines another order;
- absolute paths;
- local import aliases;
- temporary fixture directories;
- process IDs or random values.

Use stable order from prior phases:

- providers in issue #17's dependency-first order;
- independent providers by stable provider symbol ID;
- lifecycle hooks by graph order and stable hook identity;
- fields and generated helper functions by stable semantic ID;
- imports by full import path;
- files by module-relative slash path;
- diagnostics by physical source identity and stable diagnostic key;
- manifest entries by file path.

Tests must deliberately shuffle input slices and construct maps in different insertion orders. Repeating a test against already sorted fixtures does not prove determinism.

### 5. Import aliases are assigned explicitly and deterministically

Spice should emit a complete explicit import list and then format the file. It should not use `goimports` or another resolver that may search the environment, module cache, or network to decide imports.

Recommended alias algorithm:

1. Collect every required import path from the generated IR.
2. Sort by full import path.
3. Start with the loaded package's declared package name.
4. Reserve generated local identifiers and Go predeclared names that the renderer uses.
5. On collision, append a stable numeric suffix according to sorted import-path order.
6. Never emit dot or blank imports from generated bootstrap code.

The alias is an output detail. Semantic identity remains the full package import path.

### 6. Formatting needs a declared compatibility boundary

`go/format.Source` is the correct standard-library formatter for complete source files, and the renderer should fail if its output is not syntactically valid. However, the Go documentation explicitly notes that formatting changes over time.

Spice should therefore guarantee byte-for-byte stability for:

- the same Spice generator release;
- the same generation schema version;
- the same normalized target and semantic inputs;
- the supported Go formatter compatibility line recorded by the generator.

It should not promise that unrelated future Go releases can reformat old output without a diff.

Recommended policy:

- build the full source deterministically;
- run `go/format.Source` once;
- record the Spice version, schema version, and Go major/minor used by the generator in the manifest;
- make formatter/toolchain mismatch an actionable diagnostic in check mode;
- perform release migration through an intentional regeneration commit, not silent background rewriting.

The Go source header itself should remain stable:

```go
// Code generated by Spice. DO NOT EDIT.
```

Do not include the current time, source-control commit, machine path, or generator binary location in the Go file.

### 7. The manifest is the durable ownership and freshness record

A committed manifest should be a deterministic JSON document encoded from structs, not unordered maps. Conceptually:

```json
{
  "schema": 1,
  "target": "default",
  "module": "example.com/app",
  "package": "example.com/app/internal/spicegen",
  "output_dir": "internal/spicegen",
  "spice_version": "0.1.0-dev",
  "go_format_line": "1.23",
  "build_context": {
    "goos": "linux",
    "goarch": "amd64",
    "cgo_enabled": false,
    "build_flags_hash": "sha256:...",
    "environment_hash": "sha256:..."
  },
  "input_hash": "sha256:...",
  "files": [
    {
      "path": "internal/spicegen/zz_spice_gen.go",
      "sha256": "sha256:..."
    }
  ]
}
```

The exact schema can be refined. Required rules:

- paths are module-relative and use `/` separators;
- entries are sorted;
- hashes cover exact file bytes;
- no file mtime is stored;
- no absolute path is stored;
- no raw environment variable is stored;
- no secret or token is stored;
- the input hash is computed from canonical stable IR and safe target configuration, not source mtimes;
- unknown future schema versions fail closed with an upgrade diagnostic.

The manifest is not a cache. It is an ownership, compatibility, and freshness contract.

### 8. Build context is part of generated identity, but raw environment is not

Spring AOT documents that build-time conditions and profiles become fixed in generated behavior. Go build constraints create the same class of problem.

Spice generation may depend on:

- `GOOS` and `GOARCH`;
- `CGO_ENABLED`;
- explicit `-tags` and other loader build flags;
- `GOFLAGS` supplied through issue #8's environment support;
- a package driver;
- overlays in editor or test scenarios;
- workspace/module selection.

The initial disk generator should reject overlays because ephemeral editor content must not become committed generated source accidentally.

The manifest should record safe normalized fields and cryptographic fingerprints for the rest. It must never serialize the full environment because that can expose credentials, private proxy configuration, or machine paths.

Check mode must fail clearly when the current target context does not match the manifest context. It should say which safe dimensions differ and instruct the developer to select or regenerate the intended target.

The first production slice should support one declared build context per generated target. Multiple committed variants, test graphs, and build-tag-matrix generation require a separate design because Go source selected under one context may not exist under another.

### 9. Generated files should initially be committed

The default Spice workflow should be:

```text
spice generate ./...
git review generated diff
go test ./...
```

and CI should run:

```text
spice generate --check ./...
make verify
```

Reasons:

- `go generate` is not part of normal builds;
- code review can inspect exact provider calls, cleanup paths, route adapters, and module metadata;
- a consumer building a released module does not need to install or execute Spice;
- changes in generator or build environment become visible as source diffs;
- standard Go tooling sees the complete package;
- source archives contain the code that is actually compiled.

A future ephemeral overlay or build-plugin mode may be useful for editor latency, but it must not replace the committed, inspectable release artifact until it can preserve ordinary `go build`, debugging, reproducibility, and offline use.

### 10. Check mode is read-only and compares expected bytes directly

`spice generate --check` should:

1. load and validate once through the authoritative pipeline;
2. render the complete expected plan in memory;
3. read the current manifest and owned files;
4. compare schema, target context, file set, and exact bytes;
5. report all differences deterministically;
6. exit non-zero without writing anything.

Diagnostics should distinguish:

- manifest missing;
- unsupported manifest schema;
- target/build-context mismatch;
- expected generated file missing;
- generated file content stale;
- manifest-owned stale file still present;
- file hash differs from the prior manifest, indicating manual modification;
- unowned path collision;
- unexpected generated marker without manifest ownership.

For a stale Go file, a concise unified diff is useful when bounded. Large diffs should report the path, expected/current hashes, and a command to regenerate rather than flooding logs.

`spice verify` may eventually include generation freshness, as `ARCHITECTURE.md` anticipates, but the mutating and check-only APIs should remain separately callable.

### 11. Applying a plan must be guarded, not falsely described as globally atomic

A standard-library implementation can be robust without claiming a guarantee the platforms do not provide.

Recommended apply sequence:

1. Validate every module-relative path before any write.
2. Acquire an exclusive target lock using a lock file created with `O_CREATE|O_EXCL`.
3. Re-read the prior manifest after acquiring the lock.
4. Refuse unowned collisions or modified stale files.
5. Create temporary files in each destination directory.
6. Write exact bytes, sync when supported, close, parse generated Go, and verify SHA-256.
7. Replace generated content files.
8. Remove only safe stale files owned by the prior manifest and still matching its hashes.
9. Write and replace the manifest last.
10. Remove temporary files and release the lock.

Writing the manifest last makes it the commit marker. If a process crashes, the next run can detect that disk files do not match the last committed manifest and provide a recovery command.

Spice must not describe the whole operation as atomic. `os.Rename` is not guaranteed atomic on non-Unix platforms, and multiple files cannot be replaced as one standard filesystem transaction.

The lock should contain target ID, process ID, start time, and Spice version for diagnostics. Automatic stale-lock breaking is unsafe across platforms. A later explicit `--force-unlock` workflow may be added with a strong warning; the initial behavior can require the user to inspect and remove a clearly named stale lock.

### 12. Never overwrite or delete unowned work

A path is replaceable only when one of these is true:

- it does not exist;
- the prior manifest owns it and its current hash matches the prior manifest;
- it is the current target's generated file, contains the exact Spice generated marker, and a deliberate recovery mode has confirmed ownership.

Normal generation should fail rather than overwrite when:

- a user file already occupies the target path;
- a prior generated file was manually edited;
- a manifest-owned path changed type from file to directory or symlink;
- a path resolves outside the selected module;
- case-folding would collide on a case-insensitive filesystem;
- the output path uses a Windows-reserved name;
- an existing path component is a symlink.

Stale-file deletion requires both prior manifest ownership and matching content hash. This protects a developer who edited a formerly generated file or moved handwritten work into an old generated path.

### 13. Use a strict portable path policy

Before writing, normalize paths with `filepath.Clean` and convert the persisted form to slash-separated module-relative paths. Require a local relative path and reject:

- empty paths;
- absolute paths;
- `.` as a file path;
- any `..` traversal;
- NUL bytes;
- path components beginning with a platform volume escape;
- case-insensitive collisions;
- Windows-reserved device names;
- existing symlink components;
- an output root outside the chosen module after evaluation of existing parents.

Use ordinary permissions:

- directories: `0755` subject to umask;
- generated source and manifest: `0644` subject to umask;
- temporary files may start at `0600` and be changed before replacement.

Generation should not preserve executable bits or source-file permissions from inputs.

### 14. Avoid rewriting unchanged files

After rendering and hashing, compare expected bytes with the existing owned file. When they match:

- do not create a replacement file;
- do not change its mtime;
- do not rewrite the manifest unless its bytes changed;
- report the target as already current.

This improves local ergonomics, reduces noisy file watchers, and preserves Go build-cache hits. It also makes repeated generation a meaningful idempotence test.

No persistent compiler cache is needed for the first slice. Full deterministic rendering of one validated application graph should be cheap enough, and a cache would add invalidation risk before real measurements exist.

### 15. The generated package must stand alone at runtime

Generated bootstrap code may import a small stable Spice runtime for generic lifecycle coordination, but it must not require the compiler, annotation parser, `go/packages`, provider catalog, or graph builder at runtime.

The generated package should contain direct calls and typed fields. It must not contain:

- reflection-based provider lookup;
- string-keyed service location;
- a mutable global provider registry;
- runtime package scanning;
- runtime condition reevaluation for decisions fixed by the generation target;
- hidden network or filesystem discovery.

A released application should continue to build and run using ordinary Go commands when the Spice compiler binary is absent.

### 16. Generated-code errors need source provenance without machine paths

When a provider call or lifecycle hook fails at runtime, generated wrappers need stable provenance. The generator may emit stable symbol IDs and user-facing package-qualified names into error messages, but it should not embed absolute source paths.

For debugging, generated comments may reference module-relative source paths and line numbers if those values are deterministic and do not expose build-machine locations. Runtime errors should wrap the original error and name the generated phase, provider symbol, and output type.

This preserves actionable diagnostics while keeping builds relocatable and compatible with `-trimpath` expectations.

### 17. Spring capability relationship

This contract is Spice's Go-native equivalent of the build artifact boundary behind Spring Boot AOT:

- application structure is fixed and validated at build time;
- generated initialization is inspectable;
- runtime startup avoids broad reflection and discovery;
- build-time conditions are explicit inputs;
- stale generated artifacts are detected before release.

Spice intentionally differs by:

- producing ordinary Go source compiled by the standard toolchain;
- using explicit function parameters and package imports rather than bean-definition reflection;
- retaining a small runtime only for generic lifecycle mechanics;
- making output ownership and context fingerprints first-class;
- refusing silent regeneration during ordinary builds.

## Alternatives considered

### Generate directly into every provider package

Rejected for the first slice. It spreads ownership, increases collision and cycle risk, complicates deletion, and makes one application graph harder to inspect.

### Generate only in a temporary directory and compile through overlays

Deferred. It can improve editor or build latency, but the Go command documents overlay limitations, and ephemeral output weakens reviewability, ordinary module consumption, and source-release reproducibility.

### Run generation automatically from `go build` or package `init`

Rejected. The Go tool does not run `go generate` automatically, and runtime generation would require source, write permissions, compiler dependencies, and unsafe hidden side effects.

### Use `goimports` to discover imports

Rejected for the compiler core. Spice already knows exact semantic package paths. Environment-dependent import discovery adds unnecessary loading and potential network/module-cache behavior.

### Always overwrite files with the generated marker

Rejected. A marker alone is not sufficient ownership proof after manual edits, target changes, or copied files. Manifest ownership plus content hashes provide a safer boundary.

### Delete the entire generated directory before writing

Rejected. It can destroy unowned files, creates a large partial-update window, and is unsafe when output configuration changes.

### Store raw environment in the manifest

Rejected. Environment variables can contain tokens, private proxy URLs, credentials, and machine-specific paths. Store safe normalized fields and non-reversible fingerprints only.

### Promise atomic multi-file generation

Rejected. The Go standard library explicitly does not guarantee atomic rename on every supported platform, and a set of files cannot be replaced as one portable transaction.

## Proposed bounded implementation sequence

The ready backlog is already reserved for the current compiler and provider foundation. No new issue should be created until capacity opens.

When sequencing permits, split generation into bounded slices:

### Slice A — deterministic generation plan and Go renderer

Depends on issue #17.

- Define `Target`, `Plan`, `File`, and deterministic manifest structures.
- Render one target-scoped generated package and one Go file in memory.
- Implement stable import aliases and formatting.
- Add shuffled-input determinism and compile tests.
- Perform no filesystem writes from the compiler package.

### Slice B — safe apply, manifest, and check mode

Depends on Slice A.

- Add path validation, ownership rules, hashing, target lock, temp writes, manifest-last apply, no-op rewrites, and read-only check/diff behavior.
- Add crash/interruption, symlink, collision, manual-edit, stale-file, case-fold, and path-traversal tests.
- Add an offline CLI integration path.

### Slice C — generated provider construction and rollback

Depends on the provider cleanup metadata defined in the lifecycle research and on Slices A and B.

- Emit direct provider calls in issue #17 order.
- Arm cleanups immediately.
- Roll back partial construction deterministically.
- Compile and execute a real generated application fixture.

### Slice D — lifecycle and runnable command generation

Depends on lifecycle-hook metadata and Slice C.

- Emit start, stop, rollback, and graceful-run methods.
- Add real HTTP startup and shutdown integration tests.
- Keep signal and process-exit policy in generated command code rather than the reusable application API.

## Required tests for the first generation issues

### Determinism and correctness

- Same semantic model rendered repeatedly is byte-for-byte identical.
- Randomized input insertion order produces identical output.
- Import-name collisions produce stable aliases.
- Generated source parses, formats, compiles, and invokes providers in exact graph order.
- No output contains temporary roots, absolute paths, timestamps, random values, or local aliases.
- A formatter/toolchain compatibility mismatch produces an actionable diagnostic.

### Ownership and safety

- Absolute, parent-traversing, symlinked, case-colliding, and reserved-name paths fail before writes.
- An unowned target collision is preserved and fails generation.
- A manually modified owned file is preserved and fails normal generation.
- A stale owned file is removed only when its hash matches the prior manifest.
- A changed stale file is preserved.
- Raw environment values never appear in generated source, diagnostics, or the manifest.
- An overlay-backed load cannot be committed by the normal disk generator.

### Filesystem behavior

- Unchanged output preserves file and manifest mtimes.
- A concurrent target lock fails with owner details.
- Temporary files are removed after success and ordinary failure.
- An interrupted apply with an old manifest is detected on the next check.
- The manifest is replaced after content files, not before.
- Read-only check mode performs no writes.

### Integration and compatibility

- Generated files are committed and build with `go test ./...` without Spice installed at runtime.
- `GOPROXY=off` and vendor-only verification pass.
- A workspace analysis can select one explicit output module.
- An ambiguous multi-module target fails.
- Generated output works on Go 1.23.x and the current supported stable Go line.
- A real generated constructor executes in deterministic order and preserves wrapped errors.

## Exact future verification shape

A generation implementation issue should require actual output for commands such as:

```text
make verify
GOPROXY=off go test -mod=vendor ./...
go test ./compiler/generate -run TestRenderDeterministic -count=20
go test ./compiler/generate -run TestImportAliases -v
go test ./internal/genfs -run TestApplyOwnershipAndRecovery -v
go test ./internal/genfs -run TestRejectsUnsafePaths -v
go run -mod=vendor ./cmd/spice generate ./examples/hello-world
go run -mod=vendor ./cmd/spice generate --check ./examples/hello-world
go test -mod=vendor ./examples/hello-world/...
```

The exact package and command names should follow the implementation slice. The essential requirement is one real generated application that compiles and runs, plus negative executable paths for stale output and unsafe ownership.

## Open questions deliberately deferred

- Multiple independent applications in one module.
- Multiple committed GOOS/GOARCH/tag variants for one application.
- Test-only provider overrides and generated test graphs.
- Persistent compiler or generation caches.
- Language-server in-memory overlays.
- User-configurable templates.
- Generated source maps beyond module-relative comments.
- Automatic merge conflict resolution for generated files.
- Plugin or third-party generator composition.
- Splitting large generated packages across multiple files.
- Whether released generated source should include an optional project license header.

These should not expand the first renderer or apply issue.

## Final recommendation

Spice should make generated Go a deterministic, committed, target-specific build artifact with a pure in-memory renderer, explicit ownership manifest, read-only freshness check, guarded manifest-last application, and strict path and environment safety.

This gives Go developers the useful AOT and dependency-wiring outcomes associated with Spring Boot and Wire while preserving normal Go builds, inspectable source, offline execution, predictable diffs, and strong protection against stale or destructive generation.
